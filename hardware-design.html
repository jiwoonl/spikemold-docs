SpikeMold hardware design#

SpikeMold runs compiled spiking neural networks on the programmable logic (PL) of a PYNQ-Z2. The ARM processing system (PS) prepares each input, configures the accelerator and reads the result. The PL schedules the layers, tiles and timesteps and performs the sparse neuron updates. This guide describes the 100 MHz image included with the SDK.

Vivado generates design_1_wrapper as the top for this image. It contains the Zynq processing system, AXI interconnect, DMA, and sparse_board_top. The accelerator instantiates sparse_stage_top as its execution engine. See historical experiments for the retired four-stage overlay.

Board datapath#

ARM runtime
  |-- AXI-Lite --> SpikeMold control registers and DMA setup
  `-- Packed binary events --> shared DDR
                                  |
                       SpikeMold AXI input replay
                                  |
                     Row unpacker and scheduler
                                  |
                 Weight lookup and neuron-state update
                                  |
                         Spike output assembly
                                  |
                   Result AXI-Stream --> S2MM DMA
                                             |
                                     Shared DDR --> ARM runtime

Interface

What it carries

PS GP0 to AXI-Lite

Model control words, descriptors, buffer addresses, START and status. The same PS port configures the result DMA.

SpikeMold 64-bit AXI master to PS HP1

Input reads and, for plans that use DDR between stages, intermediate stream writes and reads. The accelerator’s AXI interface advertises one outstanding read and one outstanding write.

32-bit result AXI-Stream to S2MM DMA

The result frame. S2MM means stream to memory-mapped, so this DMA writes the result into shared DDR through HP1. Input replay uses the accelerator’s AXI master.

The PS supplies the 100 MHz PL clock through FCLK0. The .hwh file describes the block design and the .profile.json sidecar binds the bitstream and its runtime contract. See image selection.

What happens during a window#

  1. Load the execution plan. The compiler packages layer geometry, weight and threshold data, and the schedule in a .spm. On the board, the runtime checks the package against the image and publishes configuration through the control interface. See packages and model loading.

  2. Replay sparse rows. The runtime writes packed binary events to DDR. The input selector has four entries for the buffers used by tiled passes. Replay fetches the selected stream in bursts. The unpacker emits PAGE records for events and WATERMARK records for row progress, including empty rows. The scheduler uses this progress to decide which rows can run.

  3. Apply event updates. The frontend looks up packed signed INT4 weights for active events. It selects and adds weight contributions for groups of eight output channels. The state core stores INT16 membrane values in four banks. It applies configured arithmetic-shift decay and saturating additions in the required update order. Committing a threshold crossing emits a spike and resets that neuron to zero.

  4. Move between stages. Compact stages use on-chip row queues where the plan permits. At a DDR stage boundary, the PL packs and spools intermediate rows, then fetches them for the next stage. The hardware also schedules supported binary pooling and spatial tiles. The state-vector depth and touch FIFO depth are each 8,192 entries in this image. The admitted spatial tile limit is four. Geometry and other limits also apply. See preflight and supported operations.

  5. Return the result. The result path frames the terminal spikes and streams them to the receive DMA. The runtime checks device completion, DMA completion and result identity before decoding the output. An application can apply a host classifier to the decoded spikes. See input and result formats and application deployment.

Ordering and fault handling#

Inside the PL, a transfer takes place on a cycle with both valid and ready asserted. Buffers let producers hold data when the next block stalls. Updates to the same state retain their defined order because saturating after each update can change the result. The core can issue independent updates in parallel where the bank and ordering rules permit.

A validation fault blocks the affected transaction from publishing invalid data and records the first fault. The control path stops new work and tracks outstanding memory traffic through drain or recovery. A runtime timeout or fault can leave DMA ownership uncertain. Follow runtime recovery.

Implementation and evidence#

Evidence

Result for the included image

Routed implementation

Zynq-7020 (xc7z020clg400-1), Vivado 2025.2, 10 ns clock constraint. Worst setup slack +0.002 ns and worst hold slack +0.010 ns, with zero failing endpoints and zero routing errors.

Routed resources

37,020 LUTs, 34,983 flip-flops, 70.5 BRAM36 equivalents and 0 DSP blocks.

Native RTL simulation

Selected CIFAR and DVS fixtures each matched 32,768 golden output words.

Board functional inference

The saved-input campaign covered 15 models. Its reported latency includes ARM and PL execution. See measured results.

The included image uses unmeasured_inference=True because its hardware measurement observer does not provide valid sessions. PL-only latency, electrical energy and full-dataset FPGA accuracy remain unmeasured for this image. See deployment qualification.

For the exact selected RTL, generics and read order, use the image’s source inventory. Start with sparse_board_top for the AXI and result interfaces, sparse_stage_top for execution, sparse_row_exec for row processing and compact_if_slice for the weight and state path. The implementation record contains the routed resource report and reviewed timing exceptions. These source and build records require repository access.
