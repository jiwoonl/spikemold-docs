Runtime failure and ownership contract#

This describes the supported host runtime paths in this source tree. The listed tests use host doubles; they do not establish connected RTL, board, DMA drain, or reset behavior.

Event

Host behavior

Reuse and ownership

Invalid input before publication

Input, tag and package checks reject before result DMA is armed.

A validation rejection alone does not fault the runner. Correct the input.

Input or descriptor publication error

An exception after publication begins faults the runner, even before result DMA arm. Descriptor writes may already have taken effect.

Further runs and close/reload are rejected; all allocations are retained because quiescence is not established.

Image load fails after configuration starts

The original failure is raised and the runner faults.

All allocations remain owned; close/reload are rejected. Allocation failures before configuration publication release already allocated buffers.

Successful window

A sealed result is decoded and checked for a fault; streaming copies result data before DMA storage is reused.

The next admitted window may run.

Arm or START error

An attempted result DMA arm or subsequent START exception faults the runner, including an arm that may have partly succeeded.

Further runs are rejected before new input publication. The transfer may still own buffers.

Wait timeout, transfer error, malformed or faulted terminal

The runner faults and raises; no successful inference result is returned.

Treat the window’s state and results as invalid. Do not reuse the runner or infer partial state from counters.

Stream close

Closing a suspended stream joins its in-flight preparation and releases stream admission; it does not cancel or drain an uncertain DMA transfer.

Board close first closes the stream; closing an executing generator is rejected.

LocalPYNQTransport tracks active transfers and marks an exception during arm or wait as uncertain. It refuses release of an active buffer or any buffer after an uncertain transfer. Closing with active or uncertain ownership retains the overlay, DMA, transfer and allocations in quarantine; it does not prove that DMA has drained. A caller must not assume close() or a retry clears that ownership. The software has no general automatic safe-reset or drain procedure for an uncertain transfer; recovery needs a separately qualified target-specific drain or coordinated reset. Preserve the quarantined allocations until then.

The current public runner has no general API that proves both the core and transport quiescent after a fault. Its close and reload therefore stop with an error and retain all runner buffers, including with custom transports. Recovery requires external, target-specific proof and handling; do not clear the fault or release those allocations merely to retry. Successful image loads perform the configured CLEAR/reload sequence, which is not a proof that an uncertain DMA has drained. The runtime does not expose partially committed state as a successful result after fault. This supports discarding the whole failed window, without specifying which legal tokens the RTL must retire before its fault response. RTL must separately establish its accepted-token, drain and recovery rules, especially if its quarantine needs a coordinated reset rather than soft CLEAR.

Fault latching also retains the runner, transport and allocations in a process-lifetime quarantine, even if the caller drops the board or runner. There is currently no public API to clear that latch or release this registry; external recovery must account for the retained objects and device ownership.

The low-level result decoder can parse a sealed fault terminal and exposes its fault source, code, layer, row, address, detail and snapshot sequence. Full frames can contain state_update_accept_count, state_commit_emit_count, state_update_reject_count, state_same_addr_forward_count and coalescer_rejected_vector_count among other counters; minimal frames contain no named counters. A faulted count-mode frame must not publish channel counts. The normal runner rejects faulted terminals rather than returning those decoded diagnostics as an inference result. Counters do not by themselves prove that a failed window’s state is complete or reusable.

The proposed 8192-touch capacity change is not a public runtime or hardware profile capability: it needs its own profile, source binding and qualification before admission. Existing profile limits remain authoritative.
